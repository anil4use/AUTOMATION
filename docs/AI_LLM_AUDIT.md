# AutoFlow AI/LLM/Agent System Audit

This document provides a comprehensive audit of all AI agents, LLMs, and AI-powered features used across the AutoFlow platform. 

As of the latest architecture update, all these systems have been migrated to use the centralized **AI Control Plane (`AIRuntimeService`)**, which allows for dynamic routing, fallback models, and decoupled prompt management without altering application code.

---

## 1. Agent Chat Execution Service (`agent-chat`)
**Where it is used:** `apps/backend/src/modules/agent-chat/agent-chat.service.ts`

This is the primary user-facing conversational AI inside the AutoFlow dashboard. It allows users to execute complex multi-step tasks simply by asking for them in natural language.

### A. Sub-Agent: Execution Planner (`execution_planner`)
- **Purpose and Role:** To interpret the user's natural language request and break it down into an actionable, sequential array of operations (connector actions) that the backend can execute.
- **Rules & Constraints:** Must output ONLY a valid JSON array of objects. Cannot hallucinate steps. Must rely strictly on the provided connector schemas.
- **Capabilities/Actions:** Can search through the available connector catalog, decide the order of operations, and map parameters from previous steps. It has read access to all system connectors.
- **Level of Access:** Read-only access to connector schemas. It does not execute actions itself; it only plans them.
- **Process/Workflow:** 
  1. Receives user prompt and connector schema list.
  2. Generates a JSON plan of steps.
  3. The backend executes the plan.
- **Inputs:** `userMessage`, `catalogSchema` (List of available tools/actions).
- **Outputs:** JSON array of `plan` steps.
- **Integrations/Tools:** It uses the `ConnectorRegistry` to know what tools exist.
- **Limitations:** Dependent on the accuracy of the connector manifests. Will fail if a requested action doesn't exist in the catalog.

### B. Sub-Agent: Result Synthesizer (`result_synthesizer`)
- **Purpose and Role:** To take the raw JSON output generated by executing the plan and synthesize it into a clean, human-readable Markdown response for the user.
- **Rules & Constraints:** Do not reveal internal API structures. Use professional formatting (bolding, lists, markdown). Do not invent data not present in the results.
- **Capabilities/Actions:** Summarization and markdown generation.
- **Process/Workflow:** Receives the execution payload of the completed steps and formats the final reply.
- **Inputs:** `userMessage`, `resultsText` (JSON string of execution results).
- **Outputs:** Markdown formatted conversational reply.

## 2. In-Canvas AI Co-Pilot (`ai-agent`)
**Where it is used:** `apps/backend/src/modules/ai-agent/ai-agent.service.ts`

This is the AI assistant embedded in the Visual Workflow Builder (ReactFlow Canvas). It helps users build workflows by text prompt and mutate existing workflow configurations.

### A. Sub-Agent: Workflow Compiler (`workflow_compiler`)
- **Purpose and Role:** To translate a natural language request (e.g., "When a webhook is received, send an email") into a fully structured ReactFlow DAG (nodes and edges).
- **Rules & Constraints:** Output must be valid JSON containing `nodes` and `edges`. Must generate valid UUIDs for node IDs. Nodes must align with existing connector operations.
- **Capabilities/Actions:** Creating complete workflow templates from scratch.
- **Level of Access:** Can create workflows in the user's workspace, but does not execute them.
- **Inputs:** `userMessage`, `catalogString` (Available triggers and actions).
- **Outputs:** JSON object with `nodes` and `edges` arrays.
- **Limitations:** Complex workflows with deep conditional branching might require manual adjustment by the user after generation.

### B. Sub-Agent: Canvas Node Mutator (`canvas_mutator`)
- **Purpose and Role:** To take an existing workflow graph and a user request (e.g., "Add a delay after step 2") and modify the graph accordingly.
- **Rules & Constraints:** Must preserve existing un-related nodes and edges. Must ensure the DAG remains valid and connected.
- **Capabilities/Actions:** Modifying, deleting, or adding nodes to an existing graph context.
- **Inputs:** `userMessage`, `currentNodesStr`, `currentEdgesStr`, `baseDynamicContext`.
- **Outputs:** JSON object with updated `nodes` and `edges` arrays.

## 3. WhatsApp Conversational Agent (`whatsapp-agent`)
**Where it is used:** `apps/backend/src/modules/whatsapp-agent/agent-runtime.service.ts`

An autonomous conversational agent connected to WhatsApp via webhook, designed to engage with customers or users 24/7 on behalf of a business.

- **Purpose and Role:** To generate human-like, context-aware replies to incoming WhatsApp messages.
- **Rules & Constraints:** Must adopt a specific agent persona/personality. Must keep replies concise, friendly, and free of markdown syntax unsupported by WhatsApp (e.g., no code blocks).
- **Capabilities/Actions:** Can recall long-term memory facts, refer to user profile data (timezone, name), and hold multi-turn conversations.
- **Process/Workflow:**
  1. Incoming WhatsApp message triggers a webhook.
  2. Context (profile, memory, chat history) is assembled.
  3. LLM generates a response.
  4. Fallback logic engages if LLM fails.
  5. Response is dispatched to WhatsApp API.
- **Inputs:** `agentPersonality`, `profileSection`, `factsSection`, `currentDateTime`, `userMessage` (Chat history + current message).
- **Outputs:** A single string (the reply text).
- **Integrations/Tools:** Meta WhatsApp Cloud API.
- **Limitations:** Only text-based generation; does not generate media.

## 4. AI Data Bridge / Data Mapper (`data-bridge`)
**Where it is used:** `packages/ai-data-bridge/src/ai-data-bridge.ts` & `packages/connector-sdk/src/engine/step-executor.ts`

An intelligent data transformation engine that runs transparently in the background during workflow execution. It automatically maps data fields from a Source Step to a Target Step.

- **Purpose and Role:** To dynamically resolve field mappings when the exact key names differ (e.g., mapping `customerEmail` from Step A to `email_address` in Step B) without requiring manual user mapping.
- **Rules & Constraints:** Must respond ONLY with valid JSON containing a `fieldMapping` object and a `coercions` array. Must honor all required fields of the Target schema.
- **Capabilities/Actions:** Semantic matching, JSON schema coercion, data transformation reasoning.
- **Level of Access:** Background execution access to step payload data in-memory.
- **Process/Workflow:**
  1. Step execution engine detects missing input mappings.
  2. Source outputs and Target input schema are sent to the AI Data Bridge.
  3. LLM determines the best logical mapping between fields.
  4. The result is cached to save LLM tokens on future runs.
- **Inputs:** Context JSON containing: `source` (connector, operation, output data), `target` (connector, operation, input schema), `userOverrides`, `catalogHints`.
- **Outputs:** JSON object containing `fieldMapping`, `coercions`, `confidence`, and `reasoning`.
- **Integrations/Tools:** Interacts directly with the `workflow-engine` data payload state.
- **Limitations:** High token usage if source payload is extremely large; relies on caching after the first successful mapping to remain performant.
